# Portal API

FastAPI-приложение с DDD-слоями. По умолчанию запускается с асинхронным in-memory
репозиторием и демонстрационным порталами.

## Запуск через Docker

```bash
docker compose up --build
```

Поднимает три сервиса: `api` (FastAPI), `db` (PostgreSQL) и `frontend` (собранный React,
раздаётся через nginx с проксированием `/api/*` на `api` — как в dev-режиме фронтенда, только
без Vite). После старта:

- Фронтенд — `http://localhost:5173`
- API — `http://localhost:8000`, документация — `http://localhost:8000/docs`

Перед первым запуском (и после добавления новых миграций) нужно применить схему БД. Порт
`db` опубликован на хост, так что миграции можно накатить прямо с локальной машины:

```bash
pip install -r backend/requirements/migrations.txt
$env:DATABASE_URL = "postgresql+asyncpg://postgres:postgres@localhost:5432/portals"
alembic upgrade head
```

(для macOS/Linux — `export DATABASE_URL=...`)

### Заполнение БД демо-данными

`backend/Dockerfile.seed` собирает отдельный образ для `backend/scripts/seed_portals.py` —
он не входит в `docker-compose.yml` (это разовая задача, а не постоянный сервис), поэтому
запускается вручную:

```bash
docker build -f backend/Dockerfile.seed -t portal-seed backend

docker run --rm -e DATABASE_URL="postgresql+asyncpg://postgres:postgres@host.docker.internal:5432/portals" portal-seed
```

`host.docker.internal` — способ достучаться с контейнера до `db`, слушающего порт хоста, без
подключения к сети docker-compose (Docker Desktop на Windows/macOS понимает это имя из коробки;
на Linux без Docker Desktop нужно добавить `--add-host=host.docker.internal:host-gateway`).

Скрипт поддерживает те же флаги, что и при локальном запуске:

```bash
docker run --rm portal-seed --reset
docker run --rm portal-seed --extra 20
```

## Запуск без Docker

Требуется Python 3.11+, npm

## Backend

Требуется Python 3.11+.

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r backend/requirements/main.txt
$env:PYTHONPATH = "backend/src"
uvicorn --app-dir=backend/src main:create_app --reload
```

Для macOS/Linux вместо активации окружения используйте `source .venv/bin/activate`,
а для переменной окружения — `export PYTHONPATH=src`.


## Frontend

```bash
npm run dev
```

```bash
curl "http://localhost:8000/portals/best-action?portal_id=1"
curl -X POST "http://localhost:8000/portals/stabilize" \
  -H "Content-Type: application/json" \
  -d '{"portal_id": 1}'
```

`presentation/api/depends.py` конкретной инфраструктурной реализацией, не меняя
application-сервис и роутеры.

## Какие 5 решений я принял сам

1. Архитектура DDD, слои: Domain, Application, Infrastructure, Presentation.
2. Стэк: PostgreSQL (и Memory для тестов), FastAPI, SQLAlchemy, Alembic, Pydantic, React и т.д.
3. Все исключения придумывал и писал сам.
4. Аттрибуты портала, их основная логика, value object'ы.
5. Организация вычислений риска: нужен отдельный VO `Risk`, который считает уровень риска и факторы риска. Каждый фактор имеет своё значение и вес. Факторы сортируются по формуле (вес × значение). Первый фактор считается самым важным, по нему и считает метод `Portal.get_best_action()`. Клиент получает этот список факторов в той же сортировке по приоритету. AI только придумал формулу вычисления `Risk.value`.
6. Подтягивать данные по порталам с бэка поллингом раз в 1 минуту, при условии, что данные не подтягивались за последние 10 секунд.

## Где AI ошибся или предложил плохое решение

1. При создании имплементаций репозиториев AI положил все репозитории в один модуль без разделения на пакеты memory и postgres. А также не задал `BaseRepository` для каждого.
2. В `application/portal/service.py` AI сделал реализацию обновлений через строку, т.е. можно было указать любой несуществующий метод, и было неудобно для понимания, какие есть методы. Я создал enum для возможных методов, что избавляло от ошибки. И на всякий случай сделал отдельное исключение `InvalidPortalMethodError`.
3. Когда я попросил сделать магические методы для `ValueObject`, AI начал реализовывать эти методы отдельно для каждого VO — `Energy`, `Risk`, `ExpiresAt`, `Stability`. Я поправил его, чтобы он сделал эти методы для базового класса `ValueObject`, так как они подходят под все реализации, при необходимости можно будет переопределить их в будущем.
